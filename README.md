# Татьяна Моисеенкова — эксперт по сертификации продукции

Многостраничный сайт на Astro 6, TypeScript и обычном CSS. Статический HTML, без React и внешних шрифтов. Небольшие клиентские скрипты обслуживают форму и закрытие мобильного меню; чтение страниц, раскрытие меню и FAQ работают без JavaScript.

## Текущее состояние

Готовы 11 основных страниц, политика, отдельное согласие, 404, sitemap и robots. Имя, e-mail и Telegram заполнены реальными данными. Предоставленная фотография размещена на главной и странице «Обо мне». Домен не задан; тестовая сборка закрыта от индексации. Онлайн-отправка отключена. Прямые контакты работают.

Правовые тексты подготовлены как основа: перед сбором данных нужны фактические реквизиты оператора, условия хранения и сведения об обработчиках. Не включайте `legal.ready`, пока тексты не отражают реальный процесс.

## Запуск

Установите Node.js 24 и pnpm 11.19.0. В терминале в папке проекта:

```sh
pnpm install --frozen-lockfile
pnpm dev
```

Откройте адрес, выведенный Astro (обычно `http://localhost:4321`). Проверки и готовая сборка:

```sh
pnpm check
pnpm build
pnpm audit:site
pnpm preview
```

Готовые файлы находятся в `dist/`. Не редактируйте `dist/` вручную. `qa/seo-report.json` содержит отчет по всем HTML-страницам, метаданным, sitemap и ссылкам.

## Изменение текстов и контактов

- Основные тексты услуг, цены первого касания, FAQ и связанные услуги: `src/data/services.ts`. Стоимость также упомянута в шаблонах: при ее изменении найдите `1 500` по всему `src`.
- Тексты главной: `src/pages/index.astro`, первый экран — `src/components/HomeHero.astro`, аудитории — `src/components/Audience.astro`. Страница об эксперте: `src/pages/about.astro`.
- E-mail, имя, ссылка Telegram: `src/data/site.ts`. На странице контактов подпись Telegram берется из ссылки автоматически.
- Общий дизайн, интервалы, мобильные правила: `src/styles/global.css`.
- Пункт меню: `navigation` в `site.ts`; используйте функцию `url()` для внутренних ссылок, чтобы поддерживалась публикация в подпапке.

## Добавление услуги

Добавьте объект в `services` в `src/data/services.ts`: уникальный `slug`, `title`, `description`, `h1`, вводный текст, состав, результат, подготовка, FAQ и `related`. Шаблон автоматически создаст страницу, карточку, Service schema, хлебные крошки и запись sitemap. Укажите существующие slug в `related`. Соберите проект и запустите аудит.

Формулируйте услугу как консультацию или сопровождение. Не приписывайте Татьяне статус аккредитованного органа, выдачу сертификатов или проведение испытаний.

## Добавление статьи

В `articles.ts` уже есть шесть заданных тем с `draft:true`. Заполните `sections` массивом `{heading, text}`, проверьте факты и ссылки на актуальные источники, установите `draft:false`. В `site.ts` включите `features.blog`. Статьи и каталог создаются при сборке. Добавьте ссылку на `/blog/` в подходящий блок или footer. Черновики не имеют публичных URL и не включаются в sitemap. Не включайте пустой каталог.

Для страницы маркировки включите `features.marking` и дополните соответствующий блок в `[...future].astro`. Не включайте будущие страницы до подготовки содержания.

## Фотография

Текущее фото: `public/images/tatyana-moss.webp` (1536×1024, около 102 КБ). Оно преобразовано из предоставленного PNG в WebP без ретуши лица. Чтобы заменить его, положите новый файл в `public/images/`, измените `site.photo` и при необходимости `photoAlt` в `src/data/site.ts`. При изменении пропорций обновите размеры изображения в `HomeHero.astro` и `about.astro`, проверьте кадрирование на телефоне. Предпочтительны WebP/AVIF до 150–200 КБ. Изображение первого экрана загружается приоритетно для LCP; на странице «Обо мне» используется lazy loading. Стоковый или сгенерированный портрет не следует выдавать за фотографию эксперта.

Палитра и интервалы заданы CSS-переменными в начале `src/styles/global.css`. Заголовки используют системный Georgia, основной текст — Segoe UI с резервными шрифтами. Иконки Lucide встроены как SVG; лицензия находится в `public/images/lucide-license.txt`. Отчёт о редизайне и ссылки на локальные скриншоты: `qa/REDESIGN-REPORT.md`.

## Публикация на GitHub Pages

1. Создайте репозиторий, отправьте туда этот проект, включая `pnpm-lock.yaml` и workflow. Главная ветка workflow — `main`.
2. В Settings → Pages выберите Source: GitHub Actions.
3. В Settings → Secrets and variables → Actions → Variables задайте:
   - `PUBLIC_SITE_URL=https://ВАШ-ЛОГИН.github.io`;
   - `PUBLIC_BASE_PATH=/ИМЯ-РЕПОЗИТОРИЯ/` (для репозитория `ВАШ-ЛОГИН.github.io` — `/`);
   - `PUBLIC_SITE_LIVE=true` для готовой публичной версии.
4. Запустите Actions → Publish Astro to GitHub Pages или отправьте изменение в `main`.
5. После публикации проверьте главную, вложенную услугу, 404, `sitemap.xml` и `robots.txt`. При размещении в подпапке они лежат в этой подпапке. Google/Яндекс ищут robots в корне домена; для полноценного SEO рекомендуется отдельный домен или корневой Pages-сайт.

Workflow пропускает публикацию, пока переменная `PUBLIC_SITE_LIVE` не равна `true`, и не публикует сборку с `example.com`. В GitHub Pages включите Enforce HTTPS. GitHub Pages размещает только статический сайт; российский обработчик заявок подключается отдельно. Репозиторий проекта: https://github.com/moiseenkova1987-source/tatyana-moss-certification. Публичный сайт пока не развернут.

Официальная инструкция Astro: https://docs.astro.build/ru/guides/deploy/github/

## Собственный домен

В Pages задайте Custom domain, настройте DNS по указаниям GitHub. Для поддомена обычно используется CNAME на `ВАШ-ЛОГИН.github.io`; для корневого домена — актуальные записи из документации GitHub, не из случайных примеров. При необходимости положите имя домена в `public/CNAME`. Установите `PUBLIC_SITE_URL=https://ваш-домен.ru`, `PUBLIC_BASE_PATH=/`, пересоберите сайт и включите HTTPS. Canonical, sitemap, OG и внутренние ссылки обновятся вместе.

Локальные значения удобно хранить в `.env`, созданном из `.env.example`. `.env` не коммитится. Все `PUBLIC_*` считаются публичными: не помещайте туда пароли или API-ключи.

## Подключение формы

По умолчанию нет Formspree, сторонних приемников, платежей и отправки почты из браузера. Без backend кнопка отключена, сообщение явно сообщает, что данные не передаются. Форма также не включается без `legal.ready`, оператора и контактного e-mail.

1. Подготовьте российский HTTPS backend и российское хранение заявок; определите фактического оператора и обработчиков.
2. Заполните `site.legal.operator`, `address`, `inn`, `retention`; приведите обе правовые страницы в соответствие фактическому процессу, затем задайте `ready:true`.
3. Установите `PUBLIC_FORM_ENDPOINT=https://api.ваш-домен.ru/leads` и пересоберите проект.
4. Backend должен принимать JSON POST: `name`, `contact`, `email`, `product`, `productUrl`, `comment`, `subject`, `consent` (`accepted`), `consentVersion` (`1.0`), `requestId` (UUID).
5. Успех — только HTTP 2xx с `{"ok":true}` **после надежного сохранения** заявки. Любой другой ответ, сетевой сбой или таймаут показывают сообщение о неподтвержденном приеме; введенный текст сохраняется на странице.
6. Настройте CORS только для разрешенного домена сайта и OPTIONS для JSON. Cookies не отправляются (`credentials:omit`). Проверяйте все поля, длину и согласие повторно на сервере; ограничьте частоту запросов, размер тела и дубликаты по `requestId`. Не доверяйте данным браузера. Ведите учет версии и времени согласия на сервере, не пишите текст заявок в общедоступные логи. Отправку email выполняйте сервером через выбранную российскую инфраструктуру.
7. Проверьте настоящий успешный ответ, отказ, 500, таймаут, отсутствие согласия и повторный запрос. Браузер не делает автоматических повторов. После успешной заявки форма очищается.

Введение endpoint в конфигурацию — явное решение владельца. Автоматически проверяется HTTPS, но географию инфраструктуры код определить не может. До настройки не обещается рабочая отправка.

## Яндекс Метрика

По умолчанию аналитики нет. После определения применимых условий обработки данных добавьте официальный код своего счетчика в `Layout.astro` и актуализируйте политику. Если для выбранной конфигурации требуется согласие, загружайте счетчик только после него. Не передавайте поля формы в Метрику, URL, цели и параметры посещений; Вебвизор и запись полей не включайте автоматически. Цель успешной заявки вызывайте только в ветке подтвержденного `data.ok === true`. Сам номер счетчика не является секретом. Перед публикацией снова проверьте производительность.

## Вебмастеры и SEO

В Яндекс Вебмастере и Google Search Console добавьте фактический домен. DNS-проверка не требует изменения сайта. Для HTML-метатега задайте `PUBLIC_YANDEX_VERIFICATION` и/или `PUBLIC_GOOGLE_VERIFICATION` значением `content`, затем пересоберите. Отправьте реальный URL `sitemap.xml`.

Каждая страница содержит собственные title/description, один H1, canonical, OG/Twitter metadata. Person использует реальное имя; ProfessionalService описывает консультации, Service — конкретную услугу. FAQPage соответствует видимым раскрывающимся ответам. Рейтингов и отзывов нет. OG-image можно добавить позднее, когда появится согласованное изображение бренда.

До задания домена `PUBLIC_SITE_LIVE=false`: meta robots `noindex,nofollow`, robots `Disallow:/`. Это намеренная защита тестового сайта, а не финальная SEO-настройка. После выбора адреса задайте `true` и пересоберите.

## Блок аккредитованного исполнителя

`site.accreditation` выключен. Включайте только после заполнения реального наименования, номера записи и HTTPS-ссылки на реестр. Пока хотя бы одно поле отсутствует, блок не выводится. Он описывает фактического участника процедуры, а не статус Татьяны.

## Проверки и ограничения

`pnpm check` проверяет типы. `pnpm audit:site` проверяет готовый HTML: H1, уникальные метаданные, JSON-LD, FAQ, ссылки/якоря, согласие, sitemap и robots. Ручная проверка текста не заменяется поиском ключевых слов. Реальные Core Web Vitals зависят от хостинга, устройств и будущих фото/аналитики; обещать полевые показатели до запуска нельзя.

Итог первоначальной проверки записан в `qa/RESULTS.md`. Для повторного форматирования исходников: `pnpm exec prettier --write src scripts`. Для необязательного браузерного аудита в `scripts/browser-qa.mjs` нужен установленный Playwright и Microsoft Edge; можно передать путь к существующему модулю через `PLAYWRIGHT_MODULE`, а адрес сайта через `QA_URL` (по умолчанию `http://127.0.0.1:4322`). Скрипт использует только локальные тестовые ответы формы.

Изменения в данных, домене, endpoint и функциях требуют новой сборки. Будущие страницы по умолчанию выключены. Сборка готова к размещению после заполнения адреса публикации; прием онлайн-заявок — после настройки backend и правовых сведений.
